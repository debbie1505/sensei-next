# Admitra — Domain Context

> "From scattered to submitted."

Admitra is a student-first college application workflow platform. This document defines the canonical language of the domain.

---

## Glossary

### Admitra
The product name. Previously codenamed "Sensei" during early development. All user-facing and code references should use "Admitra".

### Supporter
A person who helps a student with their application — teachers, recommenders, mentors, or family members (including parents). In user-facing copy, use "Supporter". In code, the role is `key_person` and the table is `key_person_assignments`.

Assignment types for supporters:
- `essay_reviewer` — can view and comment on essays (used by teachers, mentors, and parents)
- `lor_writer` — writing a letter of recommendation (teachers only)

Parents sign up as Supporters and use the `essay_reviewer` assignment type. If family billing or multi-child features are needed later, a dedicated `parent` role can be introduced.

### Application College
A school the student is applying to. Stored in `application_colleges`. Contains the school name, application round (EA/ED/RD), deadline, and overall status.

### Requirement
Something a college needs from the student — an essay, recommendation letter, transcript, test score, or portfolio. Stored in `application_requirements`, linked to an Application College via `college_id`.

### Task
A unit of work with a due date. Stored in `tasks`, linked to a `plan`. Tasks can optionally link to:
- A college via `college_id` (preferred over the deprecated `school` text field)
- A requirement via `requirement_id`
- An essay via `essay_id`

Tasks are the atoms of the timeline. Not every requirement becomes a task — students or the AI generate tasks as needed.

**Task origins (MVP):**
- `admitra` — AI-generated via "Generate Timeline" based on colleges + deadlines + student profile
- `user` — manually created by the student

**Out of scope for MVP:**
- `import` — CSV or Common App integration
- `school` — counselor-pushed tasks

### Essay
The actual written content for an essay requirement. Stored in `essays`. Created lazily when the student starts writing, not when requirements are added. Linked 1:1 to a requirement of type `essay` (via `tasks.essay_id` or directly).

### Essay Review Mode
User-selected before submitting an essay for AI review. Stored in `essays.mode`.

| Mode | Behavior | Tier |
|------|----------|------|
| `light` | Quick feedback — tone, clarity, surface-level suggestions | Free |
| `standard` | Full rubric scoring with structured feedback and revision suggestions | Paid |
| `rewrite` | AI proposes a rewritten version of the essay | Paid |

Feedback structure is the same across modes; depth varies.

### School
An institution that licenses Admitra for their counselors. Stored in `schools`. Created manually during pilot onboarding (no self-service school creation in MVP).

### School-Student Relationship (MVP)
- Students can sign up without a school (B2C direct path)
- Students join a school via invite code from their counselor
- `profiles.school_id` links a student to their school
- Counselors see all students in their school via RLS

### School-Counselor Relationship (MVP)
- Counselors are linked to schools manually during pilot onboarding
- School license gives counselors dashboard access
- Student premium features are separate (per-student subscription, not bundled with school license)

### Essay Comment
Feedback left on a student's essay. Stored in `essay_comments`.

**Who can comment:**
- Supporters with `essay_reviewer` assignment
- Counselors (if student is in their school)
- AI (stored with `commenter_role = 'mentor'` for unified UX)

**Resolution flow:**
- Commenter leaves comment → student sees it on dashboard → student marks `resolved` or `ignored`
- Students resolve comments, not commenters

**Inline highlighting:**
- `target_text` stores the highlighted snippet
- Best-effort matching; may drift if essay changes significantly between versions

**Notifications:** None in MVP. Users check dashboard for updates.

### Alert
A notification for counselors about students who may need attention. Stored in `alerts`. Generated by a **daily batch job** (not real-time).

**Alert types and triggers:**

| Type | Trigger |
|------|---------|
| `missed_deadline` | Task overdue by 1+ days; only categories `essays`, `applications`, `letters` |
| `low_engagement` | No task marked `done` in 7+ days |
| `weak_essay` | AI review score < 3 (out of 5) on any `standard` mode review |
| `other` | Reserved for future use |

**Counselor actions:** Mark alert as read (`read_at` timestamp). No in-app messaging in MVP.

### Pricing Tiers (Draft — subject to validation)

| Feature | Free | Paid |
|---------|------|------|
| Dashboard, Timeline view, Essay writing | ✓ | ✓ |
| AI Timeline Generation | 1 generation | Unlimited |
| Essay Review — Light | ✓ | ✓ |
| Essay Review — Standard/Rewrite | | ✓ |
| Scholarship Matching | 5 results | Unlimited |
| Invite Supporters | 2 | Unlimited |

School licensing is separate from student subscriptions. Pricing model to be validated during pilot.

### Scholarship (kb_item)
An external funding opportunity for students. Stored in `kb_items` with `kind = 'scholarship'`.

**Data source:** Scraped from external sources (specific sources TBD). Refreshed via scheduled batch job.

**Schema fields:**
- `eligibility` (JSONB) — structured requirements (min GPA, states, citizenship, etc.)
- `embedding` (vector) — for future semantic matching
- `deadline` — scholarships with `deadline < today` are auto-hidden

**Matching (MVP):**
- **Hard filter** by eligibility fields — students only see scholarships they're likely eligible for
- Rank by tag overlap with student's `major_interests`
- Vector/semantic matching is out of scope for MVP

**UX:** Filterable list + "Recommended for you" section based on profile match. Free tier sees 5 results; paid sees unlimited.

### Plan
A timeline container scoped to an application cycle. Stored in `plans`. Tasks belong to a Plan via `tasks.plan_id`.

- Students have **one active Plan** (the most recent by `created_at`)
- Old plans are kept for history but not shown by default
- `start_date` / `end_date` define the planning window (e.g., Aug 2026 – Jan 2027)
- `title` defaults to "Class of [year] Applications" or student-defined

### Application College Status
The progress state of a college application. Stored in `application_colleges.status`.

| Status | Meaning |
|--------|---------|
| `not_started` | Added to list, no work begun |
| `in_progress` | Actively working on requirements |
| `submitted` | Application sent to college |
| `withdrawn` | Student decided not to apply |

**Outcome tracking (accepted/rejected/waitlisted) is out of scope for MVP.** Admitra's core value is getting to submission.

Status is updated **manually by student**. Auto-inference from task completion is a future enhancement.

---

## Out of Scope (MVP)

| Feature | Notes |
|---------|-------|
| Task import (CSV, Common App) | `import` origin exists in schema but not implemented |
| School-pushed tasks | `school` origin exists in schema but not implemented |
| Outcome tracking | No accepted/rejected/waitlisted statuses |
| Vector/semantic scholarship matching | Schema has `embedding` column; use field-based filtering for now |
| In-app notifications | No email or push; users check dashboard |
| In-app messaging | Counselors can't message students directly |
| Self-service school creation | Schools created manually during pilot |
| Family plans / multi-child billing | Parents use Supporter role for now |
| Auto-inference of application status | Status updated manually by student |
